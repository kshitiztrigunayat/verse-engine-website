# API changelog

Every change to the ingest API, the viewer's URL knobs and the embed SDK,
newest first, exactly as recorded when it shipped. The current contract is
the [API reference](api.md); this page is the history behind it. Entries
since 2026-08-20 are dated by the sprint window they shipped in (DevLog #7:
S1 = 22–24 Aug, S2 = 24 Aug → 5 Sep, S3 = after 5 Sep); exact commit dates
are not recorded here.

- **2026-10-25 — Pricing v2 (frozen plans), branch `pricing-v2`.** Plans are Free / Starter / Pro / Scale / Enterprise; Studio, Verse for Real Estate, All Access and the $79 Pro are grandfathered (not sold; `POST /v1/billing/checkout` answers `400` for them). Every allowance is enforced with `402 upgrade_required`, now always carrying `error`, `limit`, `used`, `plan` and **`upgrade_url`** (plus a `nudge`); new gated allowances `storageGB`, `bandwidthGB`, `apiCallsPerMonth`, `filmsPerMonth` (video exports), `capturesPerMonth`, `rendersPerMonth` (still exports). **API calls** (any `Authorization: Bearer` request except `/v1/plans`, sign-in and webhooks) are counted per account and key; near the limit responses carry **`Verse-Upgrade`**. Allowances reset on the subscription's billing date. `POST /v1/billing/checkout` takes `code` (a discount code); new `POST /v1/billing/pack {pack}` (broker packs), `GET /v1/coupons/check?code=`, `POST /v1/coupons/attribute`, `GET /v1/nudges`, `POST /v1/nudges/event`, `GET /n/<id>`. `GET /v1/account/plan` gains `meters`, `apiKeys`, `packs`, `bandwidth`, `offer`; `GET /v1/plans` gains `allowances`, `payg`, `packs`, `trialOffer`, `seatPlans` (the `apiUsage` views block is gone). `GET /v1/brand` may carry `throttle: true` (owner over bandwidth: the viewer renders lighter). See [Plan allowances](api.md#plan-allowances-402-and-the-verse-upgrade-header).
- **2026-10-25 — Release 5: capture to link (feature #1, branch `feat-capture`).** `POST /v1/ingest` (one-shot or resumable) accepts a **phone video of a room** (MP4 / MOV / WebM / AVI, recognised by container magic) or a **zip of 20–300 room photos** (no model inside), or anything with `X-Verse-Kind: capture` / begin `kind: "capture"`; it becomes a splat scene (`.vsp`, v2 under `VERSE_VSP_V2=1`) plus `ingest/<id>.stage.json` (walk view at eye height, a tour along the filmed path). While it runs the record's `stage` is `capturing` with `capture: {stage: frames|poses|training|cleanup, progress, …}`; the done record carries `path: "capture"` and `capture: {source, frames, placed, splats, timings, attempts, floor}`. New error codes `capture_too_short`, `capture_too_few_photos`, `capture_too_blurry`, `capture_no_poses`, `capture_no_floor`, `capture_empty`, `capture_unreadable`, `capture_heic`, `capture_unavailable`, `capture_failed`. WhatsApp: a video (or a video document) starts a capture and the link comes back (`VERSE_WA_CAPTURES_PER_DAY`, default 2).
- **2026-10-25 — Release 5: default camera paths, interactivity, packages.** `GET /v1/scenes/<id>/paths` gains `auto: {id, kind, edited}`; each path gains `kind` (`walk` / `drone` / `orbit`) and `auto`. New `GET · POST /v1/scenes/<id>/paths/auto` ("Reset to auto", owner; `422` when there is nothing to plan from); `?autoplay=path` and the embed option `autoplayPath` / attribute `autoplay-path`. New `GET · PUT /v1/scenes/<id>/interact` (hotspots, interactive objects, toggles; 64 KB). Telemetry `act` rows gain `cta` and `object`. The npm packages are published as `@ctruhtech/verse-sdk`, `@ctruhtech/verse-viewer`, `@ctruhtech/verse-react`, `@ctruhtech/verse-vue` (the earlier `@verse/*` names were never published). See [Camera paths](api.md#camera-paths-feature-5), [Interactivity](api.md#interactivity).
- **2026-10-24 — Release 4: web games, sign-in, billing guard, Spatial Bench.** New game routes `POST /v1/games`, `…/replace`, `PATCH /v1/games/<id>`, `PUT …/cover`, `POST …/share`, `DELETE`, `GET /v1/account/games` and `X-Verse-Kind: game` on ingest ([Web games](api.md#web-games)); games are served from the separate origin `play.ctruh.io`. Billing: `POST /v1/billing/checkout` answers the same URL while a checkout under 15 minutes old is open (`reused`) or `409 checkout_pending` with it; `/v1/billing/cancel` and `DELETE /v1/billing/checkout` clear it. - **2026-10-24 — Release 3: uploads.** A glTF packed in a zip (`scene.gltf` + `.bin` + textures) is packed into one GLB on the server; STL (binary and ASCII) is accepted; new error code `zip_invalid` (a zip without a model or missing its `.bin`). `KHR_node_visibility` is applied and dangling animation channels are dropped, with the result saying what was left out. - **2026-10-01 — 2.1.0: upload experience.** New: `GET /v1/limits` (public; enforced limits, labelled recommendations, live queue and timing), `POST /v1/ingest/<job>/contact` (name, phone, email + consent → an email when the scene is live), `GET /v1/ops/leads` (operator-only). Job records gain `attempt`, `healing`, `progress`, `etaS`, `etaText`, `queue`, `preflight`, `fixes`, `contact`, `attempts`, `stats.healed` and — on failure — `errorInfo { code, title, message, fix, retryable }`. **Behaviour changes a client can notice:** (1) a job's `error` is still a string but is now a friendly sentence with its fix, not the compiler's message — do not pattern-match it, use `errorInfo.code`; (2) files the server cannot build (not a GLB, external references, no meshes, unsupported required compression, truncated) fail at the first poll instead of after a compile attempt; (3) a GLB that lists a look-only extension (`KHR_texture_transform`, `KHR_materials_*`) as required now builds instead of failing; (4) the stages `textures (fast mode)` / `textures (safe mode)` are gone — retries report `textures` with `attempt`/`healing` — and `signing` is new; (5) `estimateS` is calibrated from recent builds when the server has history; (6) error bodies on the ingest routes carry `errorInfo` next to `error`. (7) **verify before done**: a scene is checked (integrity hash, signature, counts, bounds, texture streams, staging) before `done`; records gain `verify` and `stats.mode`, and the stages `verifying` / `publishing` are new; (8) **lossless fallback**: a job whose every build attempt fails now ends `done` with `stats.mode: "classic"`, a `?model=ingest/<id>.classic.glb` `url`, `modelUrl` (no `vpkUrl`), `fallback` and `notice` — clients that require `vpkUrl` on `done` must handle its absence; (9) **restarts**: resumable upload sessions and finished job records survive server restarts, `commit` is idempotent, `GET /v1/ingest/part/<id>` reports `job` once committed. HTTP statuses, `X-Verse-Error`, the `202 {job}` shape and every existing field are unchanged.

- **2026-09-30 — WC-6 client review pins reach the embed SDK.** The "click a spot, leave a note" workflow is no longer playground-only: `Verse.embed(el, { review: true })` (or `data-review="1"`) runs the same `review.js` machinery *inside the iframe*, with `viewer.setReviewMode(on)` to toggle it, `viewer.getComments()` to read the current list, and `verse:event` names `"review-posted"` / `"review-selected"` (`{id, pos, text}`) for the SDK's `.on()`. Private-scene embeds pass their existing `share` token (new `share` embed option, also required for `scene`/`vpk`/`model` on a private scene — a pre-existing gap this closes) straight through to the review routes, same gate as the scene bytes; anonymous visitors of an unlisted/public scene just comment with an optional name, same as the playground. Owner moderation (resolve/delete) stays playground/studio-only by design — embeds never fetch the owner-cookie check and never render those buttons. The composer clamps to the iframe's own bounds and scrolls internally, so it fits down to a 320px-wide embed. `review.js`'s core already took an explicit context object rather than playground globals; this ships the `embedded` + `onEvent` hooks that let embed-host.js drive it without reaching into playground DOM. See [embed-sdk.md](embed-sdk.md#client-review-pins-in-embeds) and the [parity table](api.md#playground-embed-parity).

- **2026-09-30 — Dedicated 4K hero texture pool.** The compiler already encoded the top `VERSE_HERO_TEXTURES` materials (default 12, source-gated ≥ `VERSE_HERO_DIM`, default 4096) at full 4096² resolution, but the runtime had nowhere to put them: every streamed blob landed in the single 2048² pool, so a hero blob was transcoded from mip 1 and its screen texel was always a 2048 resample. A second, dedicated array — tier A only, 8 slots @4096² BC7 (≤96 MB, `gpu.rs` `TIER_A_HERO_POOL_SLOTS`/`TIER_A_HERO_POOL_MAX_BYTES`) — now takes any upload that actually lands at ≥4096², so the handful of hero surfaces stream at full resolution and can never evict an ordinary 2048 resident. No new region-table column: `vg.wgsl`'s per-material `params.y` slot index is shared between the two pools (`[1, 100)` = base slot, `[100, ∞)` = hero slot, `HERO_SLOT_ENCODE_BASE` in `gpu.rs`), and both arrays are sampled unconditionally with `select()` picking the real one (same implicit-derivative rule the atlas/pool split already followed). `decode-worker.js` requests the blob's full source resolution (`maxDim=4096`) for base-color fetches only when `engine.tier` (a getter, not a method) is `"A"` and the QA tier-B override isn't set; a non-hero blob is already ≤2048 natively so this is a no-op ceiling for it, not a target size. Tier B (and the `?ssrb=1` QA override, which now also disables the hero pool — there is no other way to force tier-B behavior on a real tier-A GPU) keeps the exact old mip-1-downsample path into the base pool, unchanged. Diagnostics: `vg_hero_pool_stats()` → `[format, slots, slot_width_px, resident_count, charged_bytes_lo, charged_bytes_hi]`, forwarded to the playground as `window.__vgHeroPool` and a `· hero N/8×4096px` status-bar suffix when non-empty. QA: `web/test/fix-verify-heropool.mjs` compiles a synthetic 4096² checkerboard fixture, confirms the vpk's hero-sized blobs, and screenshots a close-up before/after — the hero pool must raise a center-crop Laplacian-variance sharpness metric over the same view with the pool forced off.
- **2026-09-30 — "Publish to Verse" for Unity ships.** `integrations/unity/com.ctruh.verse-publish` — a proper UPM package (Unity 2021.3+, `com.unity.cloud.gltfast` dependency) with a **Tools ▸ Verse ▸ Publish Scene** editor window mirroring the Blender add-on's UX: scene name (defaults to the active scene) or selection-only export, server URL + account token in EditorPrefs (token in a password field), progress from export → upload % (file-streamed `UploadHandlerFile`, HTTP/1.1) → the server's live compile `stage` passed through verbatim → done, cancel at any phase, result link with copy/open, verbatim app errors, one retry on transient/edge failures only (the `X-Verse-Error` contract), 30-minute total budget, polling on `EditorApplication.update` so the editor never blocks. The protocol layer (`VersePublishClient.cs`) is UnityEngine-free plain C#; `web/test/fix-verify-unity.mjs` replays its exact request shapes against a live local server and validates layout + the `make_tarball.sh` UPM tarball. Written against the glTFast 6.x export API; first in-editor run remains QA-6.

- **2026-09-26 — S14 HDR display output.** Viewer knob `?hdr=auto|1|0` (default `auto`): on HDR-capable displays (`(dynamic-range: high)`) a tier-A adapter configures the swapchain as `rgba16float` with extended tone mapping, so highlights past SDR white — hot speculars, emissives with intensity > 1 — drive real display headroom instead of clipping. `?hdrpeak=<linear peak>` (default 2.0, clamped [1, 8]) caps the headroom. The SDR range renders identically (goldens/fidelity are byte-stable, both run SDR); `?hdr=1` forces the float16 surface anywhere (headless tone-maps it back down), `?hdr=0` pins SDR, and a runtime display change applies on the next GPU recovery or reload. QA truth: stats fields `hdr` + `surfaceFormat`, hook `window.__verseHdr`, harness `web/test/fix-verify-hdr.mjs`.

- **2026-09-25 — API ergonomics: error contract, per-token rate limits, resumable uploads.** Four fixes surfaced by the Blender add-on work. (1) **Error contract**: every origin-generated error response now carries `X-Verse-Error: 1` and a JSON `{"error": "…"}` body — an error *without* the header came from the edge/proxy, not the app (see the [error contract](api.md#error-contract)). (2) The ingest job **`stage` vocabulary is documented** (see `GET /v1/ingest/<job>`). (3) **Per-token ingest rate limit**: requests with a valid account Bearer token draw from their own bucket (default **20/hour/token**, `VERSE_INGEST_PER_HOUR_TOKEN`) instead of the per-IP bucket (default 6/hour, now `VERSE_INGEST_PER_HOUR`-tunable) — shared NATs stop starving authenticated exporters. (4) **Resumable uploads**: `POST /v1/ingest/begin {size, name}` → `{uploadId}`, ordered `PUT /v1/ingest/part/<uploadId>` with `Content-Range` (out-of-order = `409` carrying the server's `received` offset), `POST /v1/ingest/commit/<uploadId>` → the same `202 {job}` as the one-shot path, which is untouched. Stale uploads sweep after 2 h. The Blender add-on uses the resumable flow automatically for files over 100 MB.
- **2026-09-25 — WC-6 Client review mode: pinned comments on shared scenes.** Any shared scene link becomes a review workflow: the viewer grows a "💬 Review" chip once a served ingest scene is up — a client clicks a spot (the FEAT-10 GPU pick), types a note, and the comment is pinned to that 3D position; every comment renders as a numbered DOM pin projected from world to screen, faded with distance, working in orbit and walk mode alike. New routes: `POST /v1/review/<sceneId>` `{pos, text ≤500, author? ≤40}` → `{id, t}` (rate-limited per IP, 200 comments/scene cap), `GET /v1/review/<sceneId>` → `{comments}` (private scenes need the owner's auth or a share token — the same gate as the scene bytes), `DELETE /v1/review/<sceneId>/<id>` and `POST /v1/review/<sceneId>/<id>/resolve` (owner-only; resolved pins grey out and hide behind a toggle). Storage is a per-scene append-only JSONL under the dotfile dir `ingest/.reviews/` — never served, dies with its scene on delete/eviction. `GET /v1/account/scenes` entries gain `reviews: {open, total}`. See [Review comments](api.md#review-comments).
- **2026-09-23 — WC-5 Export video: tour → MP4/WebM, client-side.** The playground viewer grows an "⬇ Export video" chip beside the ▶ Tour chip on any scene with a tour (compile-time `.stage.json` staging or a `?tour=` replay): it records the tour flythrough from the live canvas — `canvas.captureStream(0)` + `MediaRecorder`, frames requested on a fixed timeline at the chosen fps — and downloads `<scene>-tour.mp4` (H.264, where the browser muxes MP4; Chrome/Edge 126+, Safari) or `.webm` (VP9 elsewhere), the chip labeled with the real container. Options: duration (tour length default), 1080p/720p/native. During capture DRS is pinned to scale 1, demand-mode parking is blocked, and the render target runs at the output resolution; everything restores after (cancel restores too). Zero server cost — nothing is uploaded. Scripting/QA: `window.__verseExportVideo({duration, fps, height, format, bitrate, download})` resolves the Blob.
- **2026-09-20 — Private scenes & share tokens (WC-4 follow-up).** Each owned scene carries `visibility: "public" | "unlisted" | "private"` (`PATCH /v1/scenes/<id> {visibility}`, owner-only; unlisted is the default and today's exact behavior; public is reserved for a future gallery and serves like unlisted). A **private** scene's artifacts — the `.vpk`/`.vsp` plus `.stage.json`, `.plan.svg` and poster — require the owner's auth or a **share token**: `POST /v1/scenes/<id>/share` mints one (32 hex, shown once, stored hashed), `?share=<token>` or `X-Verse-Share` grants read access, `DELETE /v1/scenes/<id>/share/<shareId>` revokes. Strangers see plain `404`s (existence never advertised) with an `X-Verse-Private: 1` header so the app can say "This scene is private." **Private scenes bypass the CDN** (`VERSE_CDN_BASE`): they always serve from the origin, never `302`.
